# Specification

Decisions agreed before implementation. Changes to this document should be
discussed first.

## Goals

- Monitor 10–20 privately managed clients (scales to hundreds): disk health,
  update status and problems, software inventory, selected security and system facts.
- Server as a single Docker container, publicly reachable behind Traefik (TLS by Traefik).
- One-click agent installation without any configuration on the client;
  agents get all settings from the server, including updates.
- Read-only monitoring: no remote actions on clients.
- Alerts via SMTP, configurable on the server.
- Everything (UI, mails, code, docs) in English. Project may become open source (MIT).
- Anyone can run their own server; per-installation secrets are generated automatically.
- Areas: several users can each manage their own devices on one server
  (see [Areas](#areas)).

## Architecture

| Component | Technology |
|---|---|
| Server | Go, `net/http`, server-rendered HTML templates (no external assets, strict CSP), SQLite (pure Go, WAL) |
| Agent | Go, one static binary per platform; Windows service / systemd / launchd |
| Image | `ghcr.io/commifreak/inventory`, linux/amd64 + linux/arm64, distroless, non-root |
| CI | GitHub Actions: tests (Linux + Windows runner with real collectors), image build with signed agents |

Platforms: Windows 10/11 (amd64, arm64), Linux with systemd (amd64, arm64,
armv6/7), macOS 13+ (amd64, arm64). Windows Server and non-systemd Linux are
out of scope.

## Agent ↔ server protocol

JSON over HTTPS below `/api/agent/v1` (see `internal/protocol`). Agents use the system
proxy (environment; Windows WinHTTP + user WinINet settings incl. PAC/WPAD;
Linux /etc/environment; macOS network settings), Basic proxy auth only. Every
check-in carries agent diagnostics (proxy in use, latest 20 warnings/errors kept
in diag.json, also from offline periods), shown on the Agent tab and in the raw
export; no alert rule.

1. **Enroll** with the enrollment token from the installer → per-device credential
   (stored DPAPI-protected on Windows, root-only on Unix). The token is removed from
   the client afterwards. Reinstalls are matched by SMBIOS UUID + machine id.
2. **Check-in** every 15 min (configurable): heartbeat, returns configuration,
   update offer, "collect now" requests, revocation.
3. **Report**: collector sections (gzip), stored as latest snapshot plus derived
   history (SMART per disk/day, software changes, events).

Default collector intervals (configurable): system 12 h, SMART 4 h, updates 4 h,
software 12 h, autostart 12 h, events 4 h.

## Installers

- Windows: the same agent `.exe` for everyone; the server appends server URL and
  enrollment token ("install tag") at download time. Double-click → UAC → service
  installed → confirmation dialog. `/install /quiet` for silent installs.
- Linux/macOS: `curl … | sudo sh` script generated by the server, containing URL and token.
- Home Assistant OS: agent as Home Assistant add-on (separate public repository
  `inventory-ha-addon` with the add-on definition; public multi-arch image
  `ghcr.io/<owner>/inventory-ha-agent` built from this repository for release tags
  only; the release workflow bumps the add-on version with the secret
  `ADDON_REPO_TOKEN`). Add-on agents report `managed: home-assistant` and get no
  update offers; data from the Supervisor API (read-only role) and the host.
- Enrollment tokens can be created and revoked; revoking stops new enrollments only.
  Enrollments and installer downloads with unknown or revoked tokens are rejected
  and logged (server log as warning, audit log under *Settings → General*) with
  IP, user agent, the host's identity and only a 6-character token prefix;
  enrollments are rate limited per IP.
- Code signing (Authenticode) is planned; the tag mechanism is designed to keep
  signatures valid (certificate table). Currently unsigned.

## Self-updates

- Agent binaries ship inside the server image; the server copies them into the
  data volume so older versions remain available (newest 5 + all in use are kept).
- Signed with the project's Ed25519 key (GitHub secret `RELEASE_SIGNING_KEY`);
  the public key is compiled into the agent. Unsigned builds are never installed.
- Policy: global pause; rings `test`, `early`, `stable`, each following "latest" or
  a fixed version (promote button); per device: pin a version (also rollback) or
  "update now" (works while paused); bulk actions in the device list.
- Agent: download → hash + signature check → self test of the new binary → swap
  (old binary kept) → restart via service manager → confirm at next check-in;
  automatic rollback if the new version keeps failing. Failed attempts are
  reported and retried after 6 h.

## Collected data

- **System:** OS name/version/build, display version, edition, kernel, install
  date, boot time, time zone; hardware (vendor, model, serial, UUID, BIOS, board,
  CPU, memory, virtual); volumes with usage; network adapters (IPs, MAC, gateway,
  DNS, DHCP, Wi-Fi SSID); users (logged on, last logons, administrators).
- **Security:** Defender (state, passive mode, signature age, tamper protection);
  Secure Boot with presence of the 2023 certificates (Windows UEFI CA 2023,
  Microsoft UEFI CA 2023, Option ROM CA 2023, KEK 2K CA 2023) and Windows
  servicing status; TPM; activation; BitLocker/LUKS/FileVault; battery health.
- **SMART:** smartctl (embedded on Windows, system package on Linux, Homebrew on
  macOS), fallback to the Windows storage API; system disk flagged; external
  (USB) disks shown but excluded from alerts.
- **Memory, slots, storage controllers:** memory slots and modules (SMBIOS type
  16/17 – Windows `GetSystemFirmwareTable`, Linux `/sys/firmware/dmi/tables/DMI`;
  macOS `system_profiler`), expansion slots per firmware (SMBIOS type 9, incl.
  M.2 – the only source for empty M.2 slots, vendor quality varies), storage
  controllers with ports: Linux exact incl. empty SATA ports (libata link state),
  NVMe and SD/MMC hosts; Windows controllers by PCI class code with attached
  disks/optical drives (device tree parent), empty ports unknown; macOS occupied
  ports only. RAID controllers behind vendor tools are not inspected.
- **Updates:** Windows Update Agent (pending incl. drivers, history with HRESULT,
  last search/install, reboot pending, WSUS, services); apt/dnf/zypper/pacman
  (pending, security, last refresh/install, unattended upgrades, reboot required,
  apt history); macOS softwareupdate. Read only – caches are not refreshed.
- **Software:** Windows Uninstall registry (machine, 32/64-bit, loaded user hives;
  never `Win32_Product`), dpkg/rpm/pacman, snap, flatpak, macOS applications.
- **Autostart:** Run/RunOnce (with Task Manager enabled state), startup folders,
  scheduled tasks with boot/logon triggers, automatic services; systemd units,
  cron `@reboot`, XDG autostart, rc.local; launchd.
- **Events:** bluescreens (bug check 1001), disk/file system errors (disk 7, 11,
  51, 52, 153; Ntfs 55; stornvme/storahci 129); Linux kernel log from the
  journal merged with `dmesg` (works with volatile journals/log2ram and without
  journald): I/O and file system errors, SD card/eMMC errors (`mmc`/`mmcblk`),
  USB SSD resets, OOM kills, Raspberry Pi undervoltage; macOS kernel panics.
- **Raspberry Pi power:** throttling state from `vcgencmd get_throttled`
  (undervoltage, throttling, frequency capping, soft temperature limit – now
  and since boot), fallback to the `rpi_volt` hwmon alarm.
- **SD cards / eMMC:** listed in the disk view (no SMART); eMMC life time
  estimates and pre-EOL state are reported.

Explicitly not collected: browser data, user files, license keys, performance
time series, CPU temperatures.

## Alerts

Built-in rule catalog, each rule with enable flag, severity (warning/critical),
parameters, optional "system disk only" and optional recipient override:
device offline (default 7 days, per-device override), agent update failed,
SMART failed / reallocated / pending / uncorrectable / interface CRC errors increasing (compared with the SMART history) / temperature / SSD wear (NVMe, SATA/SAS) /
NVMe critical, low disk space, update failed, updates pending too long, update
check failing, reboot pending too long, OS end of support (endoflife.date incl. Windows LTSC/IoT LTSC cycles, fetched daily and
cached in DATA_DIR/eol, no built-in table), Office/Visio/Project (perpetual releases) end of support
(detected from the software inventory; endoflife.date "office";
Microsoft 365 Apps excluded; the UI warns when endoflife.date could not
be reached for 3 days), Defender off, Defender signatures old, Secure Boot
2023 certificates missing, not activated, system drive not encrypted (off by
default), battery worn (off by default), bluescreen, disk errors, OOM,
undervoltage (Raspberry Pi; kernel events or undervoltage present right now),
no active antivirus / third-party antivirus outdated (Windows Security Center),
firewall disabled (per profile), malware not removed / malware detected (Defender
detections), new local administrator, new autostart entry (non-OS, RunOnce
ignored), new Defender exclusion. "New" items are detected server-side against
everything ever seen on the device (`seen_items`; the first report is the
baseline, so entries that come and go with user logons do not alert) and stored
as events. Every rule can be disabled per device (Alerts tab), e.g. for a
firewall that is off on purpose.

Notifications: one mail per device and evaluation with new/still open/resolved
alerts (HTML with a plain text alternative, inline styles, light and dark colours), reminders every N hours (default 24), optional resolve mails, per-device mute.

## Areas

- Every device and enrollment token belongs to exactly one area; a user can be
  a member of several areas. Existing data moved to the area "Default" on
  upgrade, existing users became superadmins.
- **Superadmins** may do everything: global settings (updates, collection,
  alert rules, SMTP, general), users, areas, moving devices between areas.
- **Area users** see only the devices, enrollment tokens, alerts and audit
  entries of their areas (devices of other areas answer 404, also via direct
  URLs). They may change everything per device (name, notes, ring, pin, update
  now, collect now, mute, rules, offline threshold, revoke, delete), create and
  revoke tokens of their areas and set the alert recipients of their areas.
  No read-only role (could be added later). Area users cannot create users.
- Membership: OIDC groups set on the area (synchronised at every login: a new
  group adds the area, a removed group removes it) and/or manual assignment
  in the UI (kept across logins). `OIDC_ADMIN_GROUP` grants superadmin rights
  (synchronised at login); without it, superadmin rights of SSO users are
  managed in the UI. SSO users are created at their first login only if a
  group grants them access. Users who are neither superadmin nor member of an
  area cannot sign in. Rights are read on every request.
- Enrollment: a device is only recognised again (re-enrollment) within the
  area of the token used. Enrolling the same hardware with a token of another
  area creates a new device there; the old one stays in its area, goes offline
  and raises the offline alert there. Superadmins see a hint on both devices
  and can move a device with its history.
- Notifications: the recipients of a device's area get its alerts in addition
  to the global (or rule specific) recipients, without duplicate mails.
- Areas are created, renamed and deleted by superadmins; a new area gets a first
  enrollment token named after it (further tokens can be created by its users). Only empty areas
  can be deleted (their tokens are deleted with them), the last area cannot.
  The last active superadmin cannot be disabled, deleted or demoted.
- Audit entries carry their area; entries without area (logins, users, global
  settings, unknown enrollment tokens) are visible to superadmins only.
- Install page: "your tokens" are those of the areas the user is a member of,
  also for superadmins (the initial admin and existing superadmins are members
  of the first area). Superadmins additionally see a plain list (name, area,
  created, uses, state – no token values or links) of the tokens of other areas.
- Support sessions: superadmins can *sign in as* an active area user (not as
  superadmins or disabled users) from the users page. The session then has
  exactly that user's rights; a banner shows it and leads back to the own
  account without a new login. Start, end and every action are audited as
  "admin (as bob)", globally and in the user's areas; the user is not notified,
  no login time is recorded for them and their password cannot be changed.
  Signing out or the session expiring ends it; it also ends when the superadmin
  loses the superadmin rights or is disabled.

## Server security

- Local users with bcrypt passwords, forced change of the initial
  password, login rate limiting; OIDC (Authentik, Authelia, …) with group
  based superadmin rights and areas; local login can be disabled. Roles:
  superadmin and area user (see Areas).
- Sessions in the database, `HttpOnly`/`SameSite=Lax` cookies, CSRF tokens,
  strict Content Security Policy.
- Per-installation secrets generated on first start (`DATA_DIR/secrets`), SMTP
  password stored encrypted (AES-GCM).
- Agent API separated under `/api/agent/` so it can be excluded from forward auth.
- Audit log of administrative actions (per area for area users).
